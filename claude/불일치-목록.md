# 불일치-목록 (화면 요구 × DB 실제)

작성 2026-09-16 · 근거: **앱 소스 열 참조 + 마이그레이션 DDL 대조**, 그리고 **재정의된 함수 본문 직접 읽기**

> ## 이 문서를 쓰는 법
>
> - 여기 적힌 것은 **"맞다/틀리다"가 아니라 "화면과 DB가 어긋나 있다"**는 사실이다.
>   고칠지 말지는 `확정-결정사항.md`에서 정한다.
> - 열을 새로 만들면 **그 열을 읽는 화면을 같은 커밋에 넣는다.** 안 넣으면 3절에 추가된다.
> - 함수를 고치면 4절의 규칙 표를 같이 고친다. **돈이 빠지는 함수의 규칙이 문서에 없으면
>   아무도 그 규칙을 검증할 수 없다.**
>
> **측정 방법과 한계**
> - 앱의 열 참조: `.from("표")` 체인에서 `.select()` · `.insert()` · `.update()` ·
>   `.eq()/.order()/.or()` 등을 모았다. `PROPERTY_SELECT` 같은 **상수와 템플릿 문자열
>   `${...}` 를 펼쳐서** 해석했고, 중첩 관계(`property_images(url,sort_order)`)는 그 표의
>   열로 따로 넣었다.
> - **이 문서는 두 번 틀린 뒤에 나왔다.** 기록해 둔다 — 같은 실수가 다시 나온다.
>   1. 상수를 펼치지 않아 `properties.rental_yield`를 "안 쓰는 열"로 잘못 분류했다.
>      실제로는 `services/properties.ts:72`의 `PROPERTY_SELECT`에 들어 있다.
>      상수·템플릿 `${...}`·중첩 관계 해석을 넣어 다시 돌렸다. 미해결로 남은 식별자 5개는
>      전부 **스토리지 버킷 이름**(표가 아님)이라 결과에 영향이 없다.
>   2. **작업본 사본(`scan/`)이 낡아 있었다.** `store/useCurrencyStore.ts`가 아예 없었고
>      `useLocaleStore.ts`는 791바이트(실제 2000바이트)였다. 그 상태로 썼다면
>      "통화는 기기에 저장된다"고 **틀리게** 적었을 것이다. 발행 전에 `app/`(33개)·
>      `services/`(19개)·`components/`·`utils/`를 **크기 단위로 실제 파일과 대조**했고,
>      `store/`·`hooks/`는 새로 받아 다시 돌렸다.
> - DB의 열: 마이그레이션 52개의 `create table` / `add column` / `drop column` /
>   `rename column`을 순서대로 적용해 얻었다. **운영 DB를 직접 조회한 값이 아니다** —
>   7절에 확인 쿼리를 두었다.
> - "어디에도 안 쓰임" 판정: 그 열 이름이 **마이그레이션 전체·엣지 함수·앱 코드**에서
>   자기 정의문 한 줄 말고는 한 번도 나오지 않는 경우만 셌다.

### ① `profiles`는 9개 열 중 2개만 쓴다 — **가장 큰 불일치** 〔확정〕

앱이 `profiles`에서 건드리는 것은 **`id`와 `avatar_url` 뿐**이다
(`services/profile.ts:26` 조회, `:68` 갱신). 나머지 7개는 아무도 안 읽는다.

| 열 | 실제로 값이 어디 있나 |
|---|---|
| `default_language` | **기기 저장소(AsyncStorage)에만.** `store/useLocaleStore.ts` → `persistLanguage()` |
| `default_currency` | **아무 데도 저장되지 않는다.** `store/useCurrencyStore.ts`는 **메모리만** 쓴다 |
| `display_name` | `auth.users.user_metadata` (`profiles.display_name`은 `admin_search_users` RPC만 읽는다) |
| `phone` | 입력 화면이 없다 |
| `kyc_status` | 어디에도 없다 |

**따라오는 결과 2가지**

1. **통화 설정이 앱을 껐다 켜면 초기화된다** 〔확정 · 버그〕
   `useCurrencyStore`는 `create((set) => ({ currency: "USD", ... }))` 로 끝난다 —
   AsyncStorage에 쓰지도, DB에 쓰지도 않는다. MY에서 VND로 바꿔도 **다음 실행에 USD로 돌아간다.**
   파일 주석에도 *"영구 저장은 별도 Phase"* 로 남아 있다(2026-09-09 이후 진행 안 됨).
   **베트남 시장 앱의 기본 통화가 USD**라는 점도 함께 정해야 한다.

2. **언어는 기기에만 남는다.** 기기를 바꾸면 초기화된다. 푸시 알림의 언어는 이것과 별개로
   `push_tokens.lang`이 들고 있어서 **"앱에서 보는 언어"와 "푸시로 오는 언어"가 서로 다른 출처**다.

**판단 필요**: ① 통화를 최소한 기기에라도 저장할 것인가(= 버그 수정), ② 언어·통화를
`profiles`에 올릴 것인가. → `확정-결정사항.md`

### ② `properties`의 부동산 상세 수치 6개가 비어 있다 〔확정〕

`building_area` · `land_area` · `floors` · `year_built` · `occupancy_rate` · `rental_income`.
등록 화면(P2)에 입력란이 없고, 상세 화면(P1)에 표시 자리도 없다.
2단계에서 확인한 대로 **3번 마이그레이션(`property_domain_foundation`)이 만든 것**이고,
같은 마이그레이션이 만든 `developers`·`owners` 표가 비어 있는 것과 같은 이유다
(`developer_id`가 그 `developers`를 가리킨다).

리츠 플랫폼의 성격상 **면적·준공연도·임대수익은 나중에 필요해질 수 있는 값**이라,
지우는 것과 남기는 것 중 어느 쪽인지는 Dong이 정해야 한다. → `확정-결정사항.md`

### ③ `investment_products.start_at` / `end_at` — 모집 기간이 없다 〔확정〕

투자상품에 **모집 시작·종료 시각 열이 있으나 아무도 쓰지 않는다.** 등록 화면(I3)에
입력란이 없고, 목록(T3)·상세(I1)에서 기간으로 거르지도 않는다.
`investment_orders.confirmed_at`(승인 시각)도 마찬가지다 — 2단계에서 확인했듯
**주문 자체가 0건**이라 승인 흐름이 한 번도 돌지 않았다.

**투자 기능은 빌드 테스트 필수 항목**(Dong 지시)이므로, 모집 기간·승인 흐름을
**이번 빌드에 넣을지 말지**를 먼저 정해야 한다. → `확정-결정사항.md`

## 4. `set_ad_bid` — 7번 재정의된 함수의 현재 규칙 〔확정 · 본문 직접 읽음〕

최종본은 `20260913180000_ad_bid_require_active.sql`. 실행 순서대로 적는다.

| # | 검사 | 실패 시 |
|---|---|---|
| 1 | 금액이 null이거나 0 이하 | 예외 `invalid-amount` |
| 2 | placement 값이 enum에 없음 | 예외 `invalid-placement` |
| 3 | 매물이 존재하지 않음 | 예외 `no-property` |
| 4 | 매물에 업체가 없으면 — 관리자이거나 등록자 본인이어야 함 | 예외 `forbidden` |
| 4b | 그 사용자의 **승인된 활성 업체**를 찾아 매물에 붙인다 | `no-agency` |
| 5 | 매물에 업체가 있으면 — 관리자이거나 그 업체의 활성 구성원이어야 함 | 예외 `forbidden` |
| 6 | **매물 상태가 `active`여야 함** | `not-active` |
| 7 | `payment_settings`의 최소금액이 설정돼 있어야 함 | 예외 `min-bid-not-set` |
| 8 | 금액 ≥ 최소금액 | `too-low` |
| 9 | 업체 잔액 > 0 | `no-balance` |
| 10 | **자리를 아직 안 가진 매물이고** 자리가 꽉 찼으면 — 금액 > **맨 아래 자리 금액** | `too-low` |
| — | 통과 → 자리 넣기(upsert) → 정원 초과분 삭제 → 밀려난 업체 대표에게 알림 | `ok` |

정원: **추천 5자리 · TOP10 10자리** (`ad_slot_capacity`).
순위: **오직 `bid_amount` 내림차순, 같으면 `updated_at` 오름차순.**

### 불일치 ①: 앱이 요구하는 금액이 서버보다 **비싸다** 〔확정〕

| | 규칙 |
|---|---|
| **앱** (`app/ad-slots.tsx:146` `requiredFor`) | 누른 줄의 금액 **+ 1** (`BID_STEP = 1`) |
| **서버** (10번 검사) | **맨 아래 자리** 금액 초과 |

1위 줄을 눌러 사려 하면 앱은 "1위 금액 + 1"을 요구하지만, 서버는 **10위 금액만 넘으면
통과**시킨다. 서버가 느슨한 쪽이라 **보안 문제는 아니다.** 다만:

- 앱이 보여 주는 "필요 금액"은 **순위를 보장하지 않는다.** 그 금액을 내도 그 사이에
  다른 업체가 더 높게 걸면 순위는 달라진다. 서버는 순위를 약속하지 않는다.
- 앱이 서버보다 먼저 막기 때문에(`:170`) **서버라면 통과했을 금액이 화면에서 거절**된다.

**판단 필요**: "N위를 산다"는 화면 모델을 유지할 것인가, "금액을 걸면 순위는 결과일 뿐"로
바꿀 것인가. 전자를 유지하려면 서버가 순위를 검사해야 한다. → `확정-결정사항.md`

### 불일치 ②: `too-low` 하나가 서로 다른 두 실패를 뜻한다 〔확정〕

8번(최소금액 미달)과 10번(꼴찌 초과 실패)이 **같은 `too-low`를 돌려준다.**
화면은 둘을 구분하지 못해 `target.required`(앱이 계산한 값)를 메시지에 넣는데,
10번으로 실패했을 때는 **그 값이 실제 필요 금액이 아니다.**

### 확인된 것

- 자리를 **이미 가진 매물**은 10번 검사를 건너뛴다 → 최소금액 이상이면 **내릴 수도 있다.**
  앱도 같다(`requiredFor`가 내 줄이면 `minBid` 반환). **일치.**
- 앱은 `ok` / `too-low` / `no-balance` / `no-agency` / `not-active` **5개를 모두 처리**한다
  (`app/ad-slots.tsx:192~208`). 예외 3종(`invalid-*`, `no-property`, `min-bid-not-set`,
  `forbidden`)은 `failed`로 떨어진다. **누락 없음.**

## 5. `charge_ad_click` — 3번 재정의된 과금 함수의 현재 규칙 〔확정 · 본문 직접 읽음〕

최종본은 `20260912180000_ad_rules_and_deposit_min.sql`. **돈이 실제로 빠지는 유일한 자동 경로다.**

| # | 조건 | 결과 |
|---|---|---|
| 1 | placement 값이 enum에 없음 | 과금 0 |
| 2 | 그 매물·자리에 입찰이 없음 | 과금 0 |
| 3 | `active_ad_slots`에 없음 (= 지금 실제로 노출 중이 아님) | 과금 0 |
| 4 | **같은 사용자 또는 같은 IP가 1시간 안에 이미 눌렀음** | 과금 0 |
| 5 | 업체 잔액 ≤ 0 | 과금 0 |
| — | 통과 → `min(입찰가, 남은잔액)` 차감 + `ad_click_log` 기록 | 차감액 반환 |
| — | 차감 후 잔액이 0이 되면 → `depleted = true`, **그 업체의 광고 자리를 전부 삭제** | |

중복 클릭 방지는 **IP 해시**로 한다. IP는 엣지 함수(`ad-click`)가 헤더에서 읽어 해시한다 —
**앱이 보내는 값은 신뢰하지 않는다.**

빌드 테스트에서 확인해야 할 것:

| 확인 | 왜 |
|---|---|
| 같은 기기로 1시간 안에 두 번 눌렀을 때 **한 번만** 차감되는가 | 4번 규칙 |
| 잔액이 정확히 입찰가보다 적을 때 **남은 만큼만** 차감되는가 | `least(v_bid, v_available)` |
| 잔액 0이 된 순간 그 업체 광고가 **전부** 사라지는가 | `depleted` 처리 |
| 노출 중이 아닌 매물을 눌렀을 때 차감이 **없는가** | 3번 규칙 |

## 7. 확인 쿼리 (선택)

**실행 위치: Supabase 대시보드 → SQL Editor** (프로젝트 `nbfmodrxnduaxcpxgqpj`)

마이그레이션으로 재구성한 열 개수가 운영 DB와 같은지 확인한다.
아래 `예상` 값과 `실제` 값이 **모두 같으면 일치**한다.

```sql
select table_name, count(*) as 실제
from information_schema.columns
where table_schema = 'public'
  and table_name in ('properties','profiles','investment_products',
                     'investment_orders','locations','property_categories',
                     'property_documents')
group by table_name
order by table_name;
```

예상: `investment_orders` 11 · `investment_products` 22 · `locations` 7 ·
`profiles` 9 · `properties` 38 · `property_categories` 5 · `property_documents` 7

사장된 열에 값이 들어 있는지 확인한다(지우기 전에 필요).

```sql
select
  count(*) filter (where building_area  is not null) as building_area,
  count(*) filter (where land_area      is not null) as land_area,
  count(*) filter (where floors         is not null) as floors,
  count(*) filter (where year_built     is not null) as year_built,
  count(*) filter (where occupancy_rate is not null) as occupancy_rate,
  count(*) filter (where rental_income  is not null) as rental_income,
  count(*) filter (where developer_id   is not null) as developer_id
from public.properties;
```

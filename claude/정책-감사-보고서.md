# 정책 감사 보고서 — properties · property_images · investment_products

작성 2026-09-16 · 근거: **운영 Supabase `pg_policies` 실측 30건 전문**

> ## 이 문서의 성격
>
> 확정-결정사항 11은 **"본문을 읽고 보고서만 만든다. 통합 여부는 보고서를 보고 판단"**
> 이다. 그래서 이 문서는 **고치지 않는다.** 무엇이 실제로 통과를 결정하는지 적고,
> 판단이 필요한 것을 마지막 절에 모은다.
>
> **왜 개수만으로는 알 수 없었나**: RLS의 SELECT 정책은 **OR로 합쳐진다.** 가장 느슨한
> 정책 하나가 나머지를 무의미하게 만들 수 있다. 2단계에서는 개수만 셌기 때문에
> "정책이 11개니 촘촘하다"고도, "11개나 되니 엉켰다"고도 말할 수 없었다.
>
> **왜 마이그레이션 파일이 아니라 실측인가**: 이 세 표는 정책을 지웠다 다시 만든
> 이력이 있다(`properties`는 18번 마이그레이션에서 5개 삭제 후 5개 생성). 파일을
> 순서대로 읽어 재구성하는 것보다 지금 DB에 붙어 있는 것을 보는 편이 정확하다.

---

## 1. 결론

| | |
|---|---|
| 읽은 정책 | 30건 (properties 11 · property_images 10 · investment_products 9) |
| **중복·무의미한 정책** | **없음** — 통합할 것이 없다 |
| **발견한 결함** | **2건** (둘 다 property_images / properties의 **비대칭**) |
| **주의해서 볼 것** | 1건 (agency의 `featured` 직접 수정 가능성) |

**통합 판단: 하지 않는 것을 권한다.** 30건 모두 서로 다른 조건을 맡고 있다.
정책 수가 많았던 것은 엉킨 것이 아니라 **권한 경로가 셋(관리자 / 중개업소 / 개별 권한)**
이기 때문이다. 3 × (select/insert/update/delete) 구조가 그대로 개수로 나타난 것이다.

대신 **비대칭 2건**이 나왔다. 이쪽이 실제 문제다.

## 2. properties (11건)

| 동작 | 정책 | 조건 |
|---|---|---|
| SELECT | `_active_public` | `status = 'active'` — **anon 포함** |
| SELECT | `_own_agency` | `agency_id` 있고 그 업체의 활성 구성원 |
| SELECT | `_permitted` | `property_manage` **그리고** `created_by = auth.uid()` |
| SELECT | `_reviewer_or_above` | 검수자 이상 |
| INSERT | `_admin` | 관리자 |
| INSERT | `_agency` | `can_manage_agency_property(agency_id)` |
| INSERT | `_permitted` | `property_manage` **그리고** `created_by = auth.uid()` |
| UPDATE | `_admin` / `_agency` / `_permitted` | SELECT와 같은 세 경로 |
| DELETE | `_admin` | **관리자만** |

### 읽어 보니 이렇다

**공개 조회는 `status = 'active'` 하나가 전부 결정한다.** 나머지 SELECT 3건은
**비공개(draft·archived·sold) 매물을 누가 보느냐**만 다룬다 — 자기 업체 것, 자기가
등록한 것, 검수자. 넷이 겹치지 않는다.

**삭제는 관리자만이다.** 중개업소는 지울 수 없다 — 대신 `archiveProperty()`가
`status='archived'`로 바꾸는 UPDATE를 쓴다(2026-09-10 결정: 소프트 삭제가 기본).
정책과 코드가 맞다.

### ⚠ 주의 — `featured`를 직접 켤 수 있다 〔확인됨 · 판단 필요〕

`properties_update_agency`는 **어느 열이든** 고칠 수 있게 한다. `featured`도 포함이다.
`featured`는 **광고 자리를 사야 켜지는 유료 플래그**인데, 중개업소 계정이 앱을 거치지
않고 `UPDATE properties SET featured = true`를 보내면 그대로 통과한다.

완전한 구멍은 아니다 — `set_ad_bid`가 실행될 때마다 "추천 자리가 없는데 featured인
매물"을 `false`로 되돌린다. 그러나 그 정리는 **누군가 광고를 걸어야** 돌고, 그때까지는
켜진 채로 노출된다.

앱 화면에는 `featured` 토글이 없다(`property-register.tsx`에 `setFeatured` 호출이
불러오기 말고는 없다). 즉 **정상 사용으로는 일어나지 않고, 직접 호출로만 가능하다.**

→ 4단계 판단 항목.

## 3. property_images (10건)

| 동작 | 정책 | 조건 |
|---|---|---|
| SELECT | `_active_public` | 부모 매물이 `active` — anon 포함 |
| SELECT | `_own_agency` | 부모 매물이 내 업체 것 |
| SELECT | `_reviewer_or_above` | 검수자 이상 |
| INSERT | `_admin` / `_agency` / `_permitted` | 부모 매물 기준 세 경로 |
| DELETE | `_admin` / `_agency` / `_permitted` | 부모 매물 기준 세 경로 |
| UPDATE | `_admin` | **관리자만** |

### ✖ 결함 ① — `property_manage` 사용자가 **자기 사진을 못 읽는다** 〔확정〕

정책을 나란히 놓으면 바로 보인다.

| 동작 | `_permitted` 정책 | |
|---|---|---|
| INSERT | **있다** | 사진을 넣을 수 있다 |
| DELETE | **있다** | 사진을 지울 수 있다 |
| SELECT | **없다** | **읽을 수 없다** |

`properties`에는 `properties_select_permitted`가 있는데 `property_images`에는 대응하는
정책이 없다. 그래서 다음 사용자가 막힌다:

> **업체에 속하지 않고, 관리자도 아니며, `property_manage` 권한만 받은 계정**이
> **비공개(draft) 매물**을 수정하려고 열면 — 매물 본문은 보이는데 **이미 올린 사진이
> 하나도 안 보인다.**

부모 매물이 `active`가 되면 `_active_public`으로 보이므로, **비공개 상태에서만**
나타난다. 그래서 지금까지 눈에 띄지 않았다.

**왜 지금 중요한가**: 확정-결정사항 3으로 M7(계정 권한 관리)을 되살렸다. 이제
관리자가 앱에서 개별 계정에 `property_manage`를 줄 수 있다 — **정확히 이 조건의
계정이 3개 기기 테스트에서 만들어진다.** 비공개로 저장했다가 다시 여는 순간 재현된다.

재현 경로: M7에서 `property_manage` 부여 → 그 계정으로 P2에서 매물 등록(즉시 공개
끄기) → 사진 첨부 → 저장 → 내 매물에서 그 매물 수정 → **사진 목록이 비어 있다**
(`listPropertyImages`가 0건을 돌려준다).

### ✖ 결함 ② — 사진 UPDATE는 관리자만이다 〔확정 · 영향 작음〕

`property_images_update_admin` 하나뿐이다. 중개업소도, `property_manage` 계정도 사진
행을 고칠 수 없다. 지금은 앱에 사진 수정 경로가 없어(넣기와 지우기만 있다) 문제가
드러나지 않는다. **사진 순서 바꾸기(`sort_order`)를 붙이는 순간 막힌다.**

## 4. investment_products (9건)

| 동작 | 정책 | 조건 |
|---|---|---|
| SELECT | `_public` | `status in ('open','completed')` — anon 포함 |
| SELECT | `_admin` / `_permitted` | 관리자 / `investment_manage` |
| INSERT | `_admin` / `_permitted` | 〃 |
| UPDATE | `_admin` / `_permitted` | 〃 |
| DELETE | `_admin` / `_permitted` | 〃 |

**깨끗하다.** 2 × 4 + 공개 조회 1 = 9. 비대칭도 중복도 없다.
`draft`·`pending_review` 상품은 관리자와 `investment_manage` 보유자에게만 보인다 —
의도대로다.

**확정 5(모집 기간)와의 관계**: 기간 필터를 RLS가 아니라 조회 쿼리에 둔 판단이
여기서 확인된다. 이 표의 SELECT는 `status`만 본다 — 기간을 RLS에 넣었다면 MY의
내 투자가 함께 막혔을 것이다.

### D8. user_devices vs push_tokens 역할 중복
- **영향 파일**: DATABASE.md(1번, 7번, 11-4)
- **지금 결정 필요**: 아니오, 다만 Phase 2 마이그레이션에서 둘 다 만들면 나중에 정리 비용 발생
- **나중 결정 가능**: Phase 8(Push) 착수 전까지 — 단 Phase 2에서 미리 정리하면 재작업 없음
- **미결정 시 문제**: Phase 2에서 두 테이블을 다 만들어도 당장 문제는 없음(약간의 중복 컬럼), Phase 8 실제 구현 시점엔 반드시 정리 필요
- **추천안**: 통합 — `user_devices`에 `push_token` 컬럼 유지, 별도 `push_tokens` 테이블은 제거
- **추천 근거**: 기기(device)와 push token은 사실상 1:1이므로 분리 이점이 적고, 테이블 하나가 줄면 조인/정합성 관리가 단순해짐
- **결정 후 변경 파일**: DATABASE.md 1번/7번(push_tokens 제거), API.md(send-push 대상 쿼리 변경)

### D9. investment_holdings 재계산 방식(DB 트리거 vs Edge Function 트랜잭션)
- **영향 파일**: DATABASE.md(3번, 10번, 11-5), API.md(create-investment-order)
- **지금 결정 필요**: 방향성은 조기 결정 권장 — Phase 2 마이그레이션에서 트리거를 만들지 여부와 직결
- **나중 결정 가능**: 세부 구현은 Phase 5에서, 방향(트리거 vs Edge Function)은 미리 정해두는 편이 안전
- **미결정 시 문제**: 금전 정합성이 걸린 핵심 로직이라, 방향 없이 진행하면 나중에 아키텍처를 갈아엎어야 할 위험이 큼 — 27개 항목 중 리스크가 가장 큰 축에 속함
- **추천안**: Edge Function 내 단일 DB 트랜잭션(주문 확정 시 transactions INSERT + holdings UPSERT를 한 트랜잭션으로 처리), DB 트리거는 감사/보정용 보조 수단으로만 사용
- **추천 근거**: 수수료 계산·상태 전이 검증 같은 비즈니스 로직은 SQL 트리거보다 TypeScript(Edge Function)에서 다루고 테스트하기 쉬움, 트랜잭션으로 원자성 보장 가능
- **결정 후 변경 파일**: DATABASE.md 3번/10번, API.md(create-investment-order 로직 상세화)

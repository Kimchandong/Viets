# I18N.md — Viet's

버전: v0.1 (설계 초안) · 작성일: 2026-08-26

지원 언어: `vi`(베트남어), `ko`(한국어), `en`(영어), `zh`(중국어), `ja`(일본어). 원칙 17·18 — 모든 UI는 i18n 구조로 구현하며, 한국어를 기준으로 문자열을 하드코딩하지 않는다.

---

## 1. UI Translation vs Content Translation 분리

이 프로젝트에는 성격이 다른 두 가지 번역이 존재하며, 절대 같은 파이프라인으로 섞지 않는다(마스터 프롬프트 10번 항목).

| 구분 | 대상 | 저장 위치 | 갱신 주체 |
|---|---|---|---|
| **UI Translation** | 버튼, 라벨, 에러 메시지, 온보딩 문구 등 앱 자체 문자열 | 앱 번들 내 정적 리소스 파일(`src/lib/i18n/locales/{lang}.json`) | 개발자/번역가, 배포 시점에 고정 |
| **Content Translation** | 매물 설명, 투자상품 약관, 뉴스 기사 등 **DB에 저장된 사용자향 콘텐츠** | `article_translations` 테이블, `properties`/`investment_products`의 다국어 필드(jsonb 또는 관련 번역 테이블) | AI 번역 파이프라인(`translate-content` Edge Function) + Admin 검수 |

UI 문자열은 절대 DB에서 fetch하지 않는다(오프라인 시작/로딩 지연 방지, 원칙 14의 "정보성/거래성 분리"와 유사하게 "정적 UI/동적 콘텐츠"를 분리). 반대로 콘텐츠 번역은 절대 앱 번들에 하드코딩하지 않는다(운영 중 계속 늘어나는 데이터이므로).

## 2. UI Translation 구조

### 2.1 라이브러리

`i18next` + `react-i18next`(Expo/React Native 생태계 표준) 채택 제안 — Phase 3 착수 전 최종 확정.

### 2.2 파일 구조

```
src/lib/i18n/
  index.ts                # 초기화, locale 감지, fallback 로직
  locales/
    vi.json
    ko.json
    en.json
    zh.json
    ja.json
```

### 2.3 키 네이밍

네임스페이스형 dot-key, 화면/도메인 단위로 그룹화:

```json
{
  "common": { "cancel": "...", "confirm": "...", "loading": "..." },
  "home": { "title": "..." },
  "property": { "search_placeholder": "...", "filter.price": "..." },
  "invest": { "portfolio_title": "...", "risk_level.low": "..." },
  "notification": { "permission_prompt": "..." }
}
```

- 하드코딩 금지 대상: 화면에 노출되는 모든 문자열(에러 토스트, Alert, 빈 상태 문구 포함).
- 숫자/통화/날짜 포맷은 키-값 문자열이 아니라 포맷터(`Intl.NumberFormat`, `Intl.DateTimeFormat` 또는 경량 유틸)로 처리 — 언어별로 문자열을 따로 두지 않는다.
- 복수형(plural) 처리: 영어/중국어/일본어/베트남어는 단순화 가능하나, i18next의 `count` 기반 plural 규칙을 기본 채택해 향후 언어 추가에도 대응.

### 2.4 Locale 감지 및 기본값 (원칙 10)

```
앱 최초 실행
  → expo-localization으로 device locale 조회
  → device locale이 [vi, ko, en, zh, ja] 중 하나이면 해당 언어로 자동 선택
  → 아니면 기본값 'en'
  → user_preferences.preferred_language에 저장(로그인 후) / 로그인 전은 SecureStore/AsyncStorage에 로컬 저장
  → Settings 화면에서 언제든 수동 변경 가능, 변경 시 즉시 반영 + 저장
```

- 이후 앱 실행 시: 저장된 사용자 선택값이 device locale보다 우선한다(사용자가 명시적으로 바꾼 언어를 device locale 변경으로 덮어쓰지 않음).

## 3. Content Translation 구조

### 3.1 원문/번역 관계

- 콘텐츠는 항상 하나의 "원문 언어"를 가진다(뉴스 기사는 대개 vi 또는 en 원문, Admin이 직접 입력하는 investment_products는 운영자가 입력한 언어가 원문).
- `translate-content` Edge Function이 원문 → 나머지 4개 언어로 번역, 결과를 `article_translations` 등에 저장.
- 번역 실패/미번역 언어는 **원문 언어로 폴백**하고 UI에 "원문(번역 준비중)" 같은 표시를 고려(문구는 UI Translation 키로 관리).

### 3.2 대상 테이블별 처리 방식

| 테이블 | 다국어 처리 |
|---|---|
| `articles` / `article_translations` | 1:N 관계, 언어별 row (DATABASE.md 5번 참조) |
| `properties` | 매물 `title`/`description`은 운영자가 입력한 단일 언어가 기본, 자동 번역 필요 여부는 Phase 4에서 정책 확정(실거래 정보라 오역 리스크 존재 — 신중 검토 필요) |
| `investment_products` / `investment_terms` | 법적 성격이 강함 — **자동번역만으로 게시하지 않고 Admin 검수 필수**, 검수 전엔 원문 언어로만 노출 |
| `notification_templates`, `banners`, `notices`, `faqs` | `title_i18n`/`body_i18n` jsonb 필드에 5개 언어 직접 입력(운영자가 채우는 정적 콘텐츠 성격, AI 번역은 초안 제공 보조용) |

### 3.3 AI 번역과 "사실/추론 구분" 원칙 연계

AI_RESEARCH.md의 "AI가 추론한 내용과 확인된 사실을 구분" 원칙은 번역에도 적용된다 — 번역은 원문의 사실 관계를 바꾸지 않아야 하므로, `translate-content`는 요약/재해석이 아닌 **직역 우선** 프롬프트를 사용하고, 별도로 생성되는 `summary`(요약)와는 명확히 구분해 저장한다.

## 4. Admin Dashboard의 다국어

- Admin UI 자체는 1차로 `ko`/`en`만 지원(운영진 기준) — 전체 5개 언어 지원은 우선순위 낮음, 필요 시 확장.
- Admin이 편집하는 콘텐츠(공지/배너/FAQ 등)는 5개 언어 입력 폼을 모두 제공.

---

## 5. QA 관점 (QA.md와 연계)

- 신규 화면 추가 시 하드코딩 문자열 검출을 위한 lint 규칙(예: JSX 내 raw 한글/영문 리터럴 검출) 도입 검토.
- 5개 언어 전체에 대해 최소 "키 누락 없음"을 CI에서 자동 검증(예: en.json 기준으로 다른 locale 파일의 key 집합 diff).
- pseudo-localization(가짜 번역으로 레이아웃 깨짐 테스트)은 Phase 10에서 도입 검토.

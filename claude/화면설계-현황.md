# 화면설계-현황

작성 2026-09-16 · 근거: **앱 소스 33개 파일 직접 파싱** (문서가 아니라 코드)

> ## 이 문서를 쓰는 법
>
> - 앞으로 모든 대화에서 화면은 **번호로 부른다** (예: "T2 정렬 칩 수정").
> - 화면이 요구하는 표·RPC를 여기 적는다. **DB는 이 표를 따라간다.** 반대가 아니다.
> - 화면을 고치면 이 문서의 해당 줄을 같이 고친다.
>
> **추출 방법**: 각 화면의 `@/services/*` import를 서비스 함수 단위로 추적하고,
> 그 함수가 부르는 `.from()` / `.rpc()` / `functions.invoke()` / `storage.from()`을
> 모았다. 테이블명이 상수인 경우(`CONVERSATIONS_TABLE` 등)는 상수를 해석했고,
> 서비스가 다른 서비스를 부르는 경우도 따라갔다(`aiSearch` → `properties`).

## 4. 이번 파싱에서 드러난 문제

### ① A2 이메일 회원가입 — **앱에서 들어갈 수 없다** 〔확정〕

`app/register.tsx`는 완성돼 있고 `signUpWithPassword`도 정상 호출한다. 그런데
**이 화면으로 가는 `router.push`가 코드 전체에 하나도 없다.**

원인은 `app/login.tsx:19`의 주석에 남아 있다 — *"이메일/비밀번호 입력 UI(Input×2,
**회원가입 이동 Link**)를 모두 제거하고 소셜 로그인 …"*. 로그인 화면을 소셜 전용으로
바꾸면서 가입 링크가 함께 사라졌고, 대신 넣을 곳을 만들지 않았다.

현재 상태:

| 경로 | 위치 | 동작 |
|---|---|---|
| 소셜 로그인 | A1 로그인 | 정상 |
| 이메일 **로그인** | T5 MY 게스트 영역 (`my.tsx:419`) | 정상 |
| 이메일 **가입** | A2 — **도달 불가** | 막힘 |

확인 방법(3중): `router.push("/register")` 0건 · `<Link href>` 는 A2→A1 하나뿐 ·
`/register` 문자열은 `_layout.tsx`의 리다이렉트 판정에만 존재.

**판단 필요**: 이메일 가입을 살릴 것인가, 소셜 전용으로 갈 것인가. 살린다면 진입
버튼을 A1이나 T5 중 어디에 둘지. → `확정-결정사항.md` 대기 항목.

### ② M7 계정 권한 관리 — 진입 경로 없음 〔확정 · 의도됨〕

`admin-permissions.tsx`(286줄)는 완성돼 있으나 참조가 0건이다. `my.tsx:772` 주석에
*"계정 권한 관리와 등록신청 관리를 admin-agencies 하나로 합쳤다"* 고 기록돼 있어
**의도된 사장(死藏)**이다. 다만 `investment_manage` / `property_manage` 권한을
앱에서 부여할 방법이 현재 없어, 테스트 계정 준비를 SQL로만 해야 한다.

**판단 필요**: 화면을 되살릴 것인가, 삭제할 것인가.

### ③ 권한 분기의 성격이 섞여 있다 〔확인 필요〕

1절의 "권한 분기" 열은 **그 화면이 역할을 확인한다**는 뜻일 뿐, 접근을 막는지
추가 UI만 보여주는지는 구분하지 않았다. 표본 확인 결과 둘이 섞여 있다.

| 화면 | 실제 |
|---|---|
| M1·M2·M5·M6 관리자 화면 | 접근 차단 (권한 없으면 EmptyState) |
| G4 광고비 정산 | **표시 분기** — 관리자에게만 추가 블록 |
| I1 투자상품 상세 | **표시 분기** — 관리자에게만 수정 버튼 |
| P2 매물 등록 | 접근 차단 + 표시 분기 혼합 |

화면별로 어느 쪽인지 확정해 이 문서에 적어야 한다. → 3단계 작업.

### ④ 화면이 닿는 표는 19개, DB에는 35개 〔2단계에서 확정〕

화면에서 직접 읽고 쓰는 표는 아래 19개다.

```
  ad_notifications
  agencies
  agency_members
  balance_entries
  board_post_images
  board_posts
  investment_orders
  investment_products
  notification_preferences
  payment_requests
  payment_settings
  profiles
  properties
  property_ad_slots
  property_conversations
  property_images
  property_messages
  property_reports
  user_notifications
```

나머지 16개가 **불필요한 것인지, RPC·엣지 함수를 통해서만 쓰이는 것인지**는
RPC 정의를 읽어야 갈린다(예: `user_roles`는 `is_admin()` 안에서만, `ad_click_log`는
`charge_ad_click()` 안에서만 쓰인다). → `DB-마이그레이션-현황.md`에서 확정.
